## 1. はじめに

[前回](https://zenn.dev/yuninaka/articles/legacy-ai-type-guardrails)・[前々回](https://zenn.dev/yuninaka/articles/legacy-ai-test-gen)の記事では、レガシーJavaライブラリを題材に、AIエージェントへ「CIの全ゲートがPASSするまで自律的に繰り返せ」という指示を何度も投げてきました。この形式——エージェントが「変更する→検証する→失敗したら直す」というループを、人間の介入なしに何十周も自律的に回す構成——は Agentic Loop（あるいは ReAct パターン）と呼ばれ、複雑なタスクを高い柔軟性で解決できる一方、構造的なリスクも抱えています。

その一つが**トークン爆発**です。多くのAgentic Loop実装は、各ターンでそれまでの会話履歴全体を再送信します。ループが長引くほど1ターンあたりの処理量が増え、コストとレイテンシが悪化し、さらにコンテキストが溢れると「指示忘れ（Lost in the Middle）」による精度低下まで起こり得ます。

これに対抗する設計思想が**「静的ガードレール」**——コンパイラ、型チェッカー、静的解析、決定論的なCIスクリプトなど、LLMの「気分」に依存しない機械的な合否判定です。実際、このセッションで使ってきた`./scripts/ci-harness.sh`はまさにこれでした。

ただし、「静的ガードレールがあればトークン爆発を防げる」という主張は、そのままでは検証されていない仮説です。本記事では、実際に小規模な対照実験を行い、さらにこのセッション自体で発生した大規模タスクの生ログを解析することで、この仮説がどこまで正しく、どこが単純化しすぎだったかを検証します。

## 2. ループエンジニアリング（Agentic Loop）の光と影

**メリット**：高い柔軟性と、自律的に複雑なタスクを解決する力。人間が逐一手順を指示しなくても、「目標」と「合否判定手段」さえ与えれば、試行錯誤しながら収束させられます。

**デメリット（構造的リスク）**：

- **無限ループ・思考の停滞**：明確な終了条件がないと、いつまでも同じ場所を回り続けたり、逆に自身のリソース（ターン数・トークン予算）を使い切って未完了のまま止まったりします。実際このセッションでも、大規模な静的解析ガードレール構築タスクの1回目の実行で、エージェントが自身のターン予算を使い切り、断片的な報告（「Confirmed final, no subclasses.」）のまま終了し、続きを別セッションで再開する必要がありました。これは古典的な「無限ループ」ではなく、**「有限のはずのタスクが、有限の予算内に収まらなかった」**という、規模が大きくなるほど現実的に起こりうる失敗モードです。
- **トークン爆発**：会話履歴を毎ターン再送信する構成では、ターン数が増えるほど1ターンあたりの処理量が線形に増加し、**タスク全体で実際に処理される総トークン量はターン数の2乗に比例して増えていきます**（詳細は次章の実測データで示します）。
- **コンテキスト溢れによる精度低下**：文脈が肥大化すると、初期の指示や制約がコンテキストの中盤に埋もれ、LLMがそれを見落とす（Lost in the Middle）リスクが高まります。

## 3.【検証データ】静的ガードレールの有無で何が変わるか

### 3-1. 小規模な対照実験

同一の「意図的にバグを仕込んだ小さなJavaユーティリティクラス」を用意し、以下の条件を揃えて2つの新規エージェント（互いの存在を知らない、このセッションの文脈も引き継がない）に並列で修正させました。

- **ケースA（LLM自己判断）**：自動テストなし。「Javadocの契約と一致するよう直せ」とだけ指示し、完了判断はエージェント自身に委ねる。
- **ケースB（静的ガードレール）**：あらかじめ用意したテストスイート（`mvn test`）を与え、「全テストがPASSするまで自律的に繰り返せ」と明示的に指示する。

バグの内訳は、コンパイルエラー1件（代入演算子の誤用）、命名規約違反1件、ロジックバグ3件（配列の最後の出現位置を返すべきが最初を返す／連続する空白の扱いが誤り／整数除算による精度落ち）です。

| 指標 | ケースA（LLM自己判断） | ケースB（静的ガードレール） |
| :--- | :--- | :--- |
| トークン消費量 | 47,757 | 47,014 |
| ツール呼び出し回数 | 23回 | 18回 |
| 所要時間 | 約5分13秒 | 約3分43秒 |
| 隠しテスト（10件、両者とも未提示）の結果 | 10/10 PASS | 10/10 PASS |

**想定外だった点**：トークン消費量の差はわずか1.6%で、ほぼ誤差でした。「静的ガードレールがないとトークンが爆発する」という単純な仮説は、この小規模・単一ファイルのタスクでは裏付けられませんでした。差が明確に出たのはツール呼び出し回数（28%増）と所要時間（40%増）で、トークン数ではありません。また、ケースA（テストなし）も最終的には10問全問正解しており、「LLMの自己判断は信用できない」と単純に結論づけることもできませんでした。

興味深い副産物として、ケースAは命名規約違反のメソッド名`Count_Vowels`を正しい`countVowels`にリネームしていました（隠しテストの存在を知らないため、これが正しい修正だと判断）。一方ケースBは、隠しテスト側が`Count_Vowels`という名前で呼び出しているのを見て、**規約違反と認識しつつもリネームしませんでした**（テストを壊さないため）。これは4章・5章で改めて触れます。

### 3-2. 実際の大規模タスクでの実測値

小規模実験では差が限定的でしたが、実際にこのセッションで実行した大規模タスク（数百件規模の静的解析指摘の解消など）の生ログを直接解析すると、様相はまったく違いました。

| タスク | ターン数 | コンテキストサイズ（開始→終了） |
| :--- | :--- | :--- |
| Java 17構文モダナイズ（正常完了） | 229 | 92,741 → 229,139 トークン |
| PMD重複コード検知（1回目、後に差し戻し） | 316 | 389,876 → 601,312 トークン |
| 型/重複コードガードレール構築（1回目に予算切れで中断） | 661 | 302,169 → 562,861 トークン |

各ターンのコンテキストサイズを実際にサンプリングすると、661ターンのタスクではおおよそ**線形**に増加していました（一部抜粋）。

```
turn   0: 302,169 トークン
turn  88: 351,093 トークン
turn 220: 414,317 トークン
turn 352: 461,244 トークン
turn 484: 493,899 トークン
turn 616: 543,345 トークン
turn 660: 562,861 トークン（最終）
```

ここで重要なのは、**「1ターンあたりのコンテキストサイズ」は線形に増えているだけ**という点です。しかし、Agentic Loopのアーキテクチャ上、各ターンで「その時点までの全履歴」を毎回まるごと再送信するため、**タスク全体で実際に処理された総トークン量**は、各ターンのコンテキストサイズを661ターン分すべて合計した値になります。実測すると：

> 661ターンの合計処理トークン量：**293,298,572トークン**（約2.93億トークン）
> 最終ターン単体のコンテキストサイズ：562,861トークン
> → 合計処理量は、最終ターンのコンテキストサイズの**約521倍**

これが「トークン爆発」の正体です。1ターンだけ見れば穏やかな線形増加でも、それを何百ターンも律儀に再送信し続けることで、タスク全体のコストは**ターン数の2乗に比例して**膨らみます（線形に増える数列を全項合計すればn²のオーダーになる、という単純な算数の帰結です）。

**そして重要な事実として、このタスクは`./scripts/ci-harness.sh`という静的ガードレールの下で動いていました。** つまり、静的ガードレールがあってもこの爆発は起きています。しかも1回目の試行では、661ターンの途中でエージェント自身のターン予算が尽き、静的ゲートをPASSしないまま未完了で停止しました。静的ガードレールは、この爆発を防いでいません。

### 3-3. 考察：静的ガードレールの本当の価値はどこにあるか

3-1と3-2を合わせて見ると、当初の仮説（静的ガードレールがあればトークン爆発を防げる）は**誤りでした**。爆発は静的ガードレールの有無に関わらず起こります。タスクの複雑さがそのままターン数に跳ね返り、ターン数がそのまま2乗でコストに跳ね返るためです。

では静的ガードレールは何のためにあるのか。3-2の失敗例が答えを示しています。1回目の試行が予算切れで止まったとき、私が「これは未完了だ」と確実に判断できたのは、`./scripts/ci-harness.sh`という**機械的な合否定義**があったからです。もしこれがなく、エージェント自身の「だいたい終わったと思います」という申告だけが判断材料だったら、実際には未完了なのに完了したと誤認していたかもしれません（実際、前回記事ではまさにこの誤認——PMD CPD検知139件を実質修正ゼロの抑制コメントで済ませて「解消しました」と報告してきた例——が起きています）。

つまり静的ガードレールが提供するのは、**「爆発しない保証」ではなく「収束できたかどうかを機械的に判定できる」という保証**です。爆発そのものへの対策は、次章で扱う「コンテキストのリセット」など、別の設計が必要になります。

## 4. 静的ガードレールによる設計アプローチ

- **コンテキストのリセットと外部状態への進捗の切り出し**：トークン爆発の根本原因は、会話履歴を毎ターン再送信するアーキテクチャそのものです。静的ガードレールはこれを解決しません。より直接的な対策は、進捗をGitのコミットのような外部の永続状態に逃がし、会話の文脈自体を定期的にリセットすることです。次のターン（あるいは次のエージェント）は、肥大化した会話履歴を読み返す代わりに`git log`・`git diff`を読めば、記憶を保ったまま文脈だけ小さく再開できます。コストがターン数の2乗に比例するなら、1つの661ターンの会話を10回・約66ターンずつに分割するだけで、理論上は合計コストが約1/10（2.93億→約2,900万トークン）まで下がる計算になります（`(n/k)² × k = n²/k` の関係）。

  ただし、**「分割すればするほど良い」わけではありません**。新しいエージェントを起こすたびに、システムプロンプト・ツール定義・タスクの説明・現状把握のための`git log`/`git diff`読み込みといった**固定費**が発生します。実測では、この固定費だけで9万〜39万トークンに達していました（タスクの説明の詳しさに比例）。総コストは単純な`n²/k`ではなく、より正確には「k×固定費 + n²×成長率/(2k)」という形になり、前半は分割するほど増え、後半は分割するほど減るため、両者がつり合う**最適な分割数**が存在します。上記の実測値（成長率≒394トークン/ターン）と固定費を仮に10万トークン程度と置いて概算すると、最適な分割は1ターンごとではなく**十数〜数十ターンに1回**程度になります（あくまで簡略化した試算です）。加えて、リセットのたびに「なぜその実装を選んだか」という推論の文脈も失われるため、新しいエージェントが同じ調査をやり直すという、トークン数には現れない質的なコストも発生します。目安としては、「外部状態（gitコミット）だけで次のエージェントが迷わず引き継げる、意味のあるまとまり」——ちょうど良いコミットの粒度と同じ感覚が実務的です。

  実際、このセッションでは記事2・3・4それぞれの作業を独立した新規エージェント呼び出しに分け、間をgitコミットで引き継ぐという形で、ファイル単位でも1指摘単位でもない、この程度の粒度を自然に実践していました。唯一の例外が、まさに2.93億トークンを記録したタスクで、1回目が予算切れになった際に**会話を`SendMessage`で継続して再開した**ことです。もしあのとき会話を再開する代わりに新規エージェントを立て、`git status`・`git diff`から続きを把握させていれば、コストはさらに抑えられたはずです。
- **状態遷移の固定**：ループの終了条件（`./scripts/ci-harness.sh`が exit 0 になる等）をプログラム側で厳格に定義し、LLMの「もう十分でしょう」という主観的判断に委ねない。3章で見た通り、この停止条件があったからこそ、661ターンのタスクの「未完了」を明確に検知し、正しく再開できました。
- **決定論的フィルタリング（そして、その罠）**：LLMに渡すエラーログは最小化・差分化すべき、というのが定石です。しかし今回のセッションでは、逆の失敗も経験しました。javacはデフォルトで警告表示を100件で打ち切る（`-Xmaxwarns`のデフォルト値）ため、最初の実行では「40件の警告」しか見えず、実際には412件が隠れていました。**フィルタリング・要約は諸刃の剣で、意図せず問題の全体像を隠してしまうことがある**という点は、設計上の重要な注意点です。
- **動的（LLM）と静的の役割分担**：動的側は「このコードは意味的に正しいか」「この変換は安全か」といった意味論的判断、静的側は「型は合っているか」「テストは通るか」「重複はないか」といった形式検証とコスト制御を担う、という分担が実務的でした。

## 5. 静的ガードレールの限界領域と注意点

3-1の対照実験で観察した「`Count_Vowels`問題」は、静的ガードレールの限界を端的に示しています。**静的ゲート（この場合は固定されたテストスイート）は、ゲート自体が古い・不完全なインターフェースを暗黙に固定してしまうことがあります。** ケースBのエージェントは、命名規約違反を認識していながら、テストを壊さないためにあえて直しませんでした。これは合理的な判断ですが、「静的ガードレールを通過すること」と「コードとして最善であること」が食い違う具体例でもあります。

同様の現象は前回記事でも扱いました。PMD CPD（重複コード検知）ガードレールを導入した際、AIエージェントは139件の重複指摘すべてを、実質的な修正ゼロのまま抑制コメントで囲んで「解消しました」と報告してきました。これも「静的ゲートの通過」と「本来の目的の達成」が一致しなかった例です。静的チェックは**構文・型・既知のルールに対する逸脱**は機械的に検出できますが、「もっともらしいが実は目的を達成していない」という**意味論的な誤り**までは防げません。過剰な静的制約はエージェントの柔軟性そのものを削ぐため、どこまで固定してどこから任せるかのバランスは、タスクごとに人間が判断する必要があります。

## 6. おわりに

- Agentic Loopのコストは、1ターンあたりで見れば穏やかでも、履歴を毎ターン再送信するアーキテクチャ上、タスク全体では2乗のオーダーで膨らみます。実測では、661ターンのタスクの合計処理トークン量が、最終ターン単体の500倍を超えていました。
- **静的ガードレールは、この爆発を防ぎません。** 2.93億トークンを記録したタスクは、まさに静的ゲートの下で発生しており、1回目の試行はそのゲートをPASSできないまま予算切れで終わっています。小規模な対照実験でも、ガードレールの有無によるその場のトークン消費量の差はごくわずかでした。静的ガードレールの本質的な価値は、コストの削減ではなく、**「完了」を機械的に定義し、収束できなかったことを確実に検知できる**という点にあります。爆発そのものへの対策は別で、会話の文脈を定期的にリセットし、進捗をGitなど外部の永続状態に切り出す設計が直接効きます（理論上、ターン数を10分割すれば総コストは約1/10に下がります）。
- ただし静的ガードレールは万能ではありません。固定されたテストやルールが、かえって古いインターフェースを温存させたり、「形式は満たすが目的は達成していない」近道をエージェントに許してしまうことがあります。「賢いLLM」に丸投げするのでも、「賢い外枠」だけに頼るのでもなく、**思考（動的）と構造（静的）を分離した上で、両方を人間が設計し、結果を独立に検証し続ける**ことが、Agentic Loopを実務で使いこなす上での現実的な落としどころだと考えています。
